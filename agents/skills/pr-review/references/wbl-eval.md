# Repo hook: wbl-eval

Applies when any changed path is under `eval/wbl-eval/` in the solar-system monorepo. House rules W1 to W4 apply too.

## Reading mandates

- `eval/wbl-eval/docs/GUIDELINE.md` is the review contract. The directory's `CLAUDE.md`/`AGENTS.md` requires reading it in full before reviewing a benchmark PR and stating in the review notes that you did; do that, in small chunks so nothing is truncated. Read it at `target_sha` (what the merged code must satisfy) and diff it against HEAD and `merge_base` for `convention_drift` (SKILL.md Phase 0.6). Policy that landed on the base after the PR branched (result-contract fields, error-handling rules, documentation requirements) binds the merged code; a PR that does not adopt it is an `integration` finding (L5).
- The eval wiki lookup is mandatory too: the clone lives at `eval/wbl-eval/eval-wiki` in a solar-system checkout (any Orca worktree under `~/orca/workspaces/solar-system/*/` or the main checkout). Start from `wiki/index.md`, open the pages for the benchmarks and subsystems the diff touches, follow their related links, and verify every load-bearing claim against code, registry files, or the original source; where the wiki and the code disagree, the code wins. The `wiki/repo/**` mirror describes the code at a later commit than an old PR head, so it can leak later fixes into a review of an earlier head; read code for anything about the reviewed revision. Cite the wiki pages you used in the report, never in a comment (house rule G2). If the clone is missing, say so.
- Item numbers drift as the guideline grows (the base contract moved from item 13 to item 15 in 2026). Confirm every number you cite against the copy you read.

## Review procedure: the guideline's own loop, in its order

The guideline's operating loop and its review-only checks are the backbone of a wbl-eval review (SKILL.md R13). Run them before the generic risk map and report them as the Guideline checklist.

1. **Pre-read.** Read `docs/GUIDELINE.md` in full at `target_sha` and record it as the first checklist row ("read in full at <sha>"). Diff it against HEAD and `merge_base` for drift.
2. **Item 0 first.** Before any implementation detail, check the complete changed-file list (from `git diff --name-status <merge_base> HEAD` in `WT`; `gh pr view --json files` stops at 100), including added files, renames, files outside the benchmark directory, and files inside copied upstream trees. Every file must serve the PR's stated scope.
3. **Build the checklist for this PR's type** from the table below, then run each item's *Verify* step as the guideline words it, separately for every execution path the PR adds (for example host Docker and E2B, a mirrored dataset and a local data directory): a benchmark that rejects missing input on the host path but turns the same failure into a 0.0 score inside the sandbox path violates item 15f. Record pass, violation, n/a, or not-checked with evidence for every row.
4. **Run the review-only checks.** The guideline's "Known gaps (not machine-enforced)" section lists checks `make param-check` does not do; run every one that applies (at the time of writing: item 0, items 25a to 25c, 25b's official-promotion evidence, 28's `migration.md` completeness, tier placement (25), experiment-file exhaustiveness (26), benchmark-arg order against sibling specs (16), canonical names (P6), base-contract items 15d to 15f, the static half of resume (27, P11), wbl-authored nested timeout keys, and a variant module that builds `info` by hand next to a conforming one (rule 25)). Re-read that section each time; it changes.
5. **Run the gate.** `make param-check` (inside `WT` with a scratch environment, R9) must print the literal success line. For mass registry or rename changes, check which verification-playbook proofs (Part C) the PR states and rerun the cheap ones (construct-all smoke, instance-attribute diff, failure-set diff).
6. **Check the PR body's proofs.** Operating-loop step 7 requires authors to state the file-scope check, required documentation and official-promotion evidence (items 0, 25a, 25b, 25c, 28), and the "scoring unchanged ≠ scores unchanged" distinction (P8) when the generation plumbing of an existing benchmark moved (a new benchmark or variant has no earlier scores to compare, so P8 does not ask it for that sentence). A proof that is present but false is a violation of the item it proves, not a pass. Quote the author's statement for each one that applies. A list of changed areas or test runs is not a scope-check statement, and your own scope check does not supply the author's. The documentation proof is present when the body names the documents and sections it updated and the review finds no overview, scoring, or retry row this change left stale; a list of edited files falls short only when such a stale row exists, and then the comment names it. Missing or contradicted proofs become one short general PR comment that asks only for those, without prescribing wording, not one inline comment each.
7. **Documentation checks for every affected spec (25a to 25c).** Applicability comes from the behavior the PR changes, not only from changed registry files: a maintained document whose usage or retry statement the change makes false brings 25a and 25c into scope. A verified wrong setup or usage instruction in a maintained document makes 25a a violation, and touched comments are swept against the actual behavior (P7), including behavior the PR removed. For each new or changed YAML, including `.light` and archived variants affected through a shared benchmark, provider, judge, or harness: an exact overview row in `registry/evals/README.md`, a scoring row in the owning README's `오류 처리와 재시도` section, a retry row in the benchmark's `Retries, timeouts and resume` section, a YAML header note linking the overview row, links and anchors that resolve, and a retry note that matches the effective call paths. Trace the settings through the implementation; do not take the rows on trust. Treat these as separate checks and separate drafts, so one finding does not satisfy the others: one retry section per benchmark directory, a literal total for every layer, the retry conditions, whether `api_max_attempts` has an effect (or a statement that it has none), and, for item 27, the documented reason when resume is declined. Read the retry prose, not only the links: every API, task, SDK, and infrastructure layer needs a literal total attempt count, its retry trigger, its stop condition, and how registry settings change it ("native", "task-specific", or "SDK-controlled" is not a count). A new trigger for a shared retry path (for example a new error pattern that a shared bridge retries) requires updating the shared `src/wbl_eval/evals/benchmarks/README.md` even when the path was undocumented before.
8. **Parameter fidelity needs the wire (items 1, 5, 7, P10).** A pass needs the outgoing request of the final client at its pinned version: for each non-null profile value, the emitted config, the client or SDK option, and the wire key and value, plus a probe with a budget above any client cap and with an explicit off value. A value written only into model metadata, a catalog, or a preflight check is not forwarded. If the client cannot be fetched or run, these items are `not-checked`.
9. **Failure outcomes per backend (items 10, 10b, 15f, P9).** For each execution backend the PR supports (host Docker, E2B, Modal, API), push a missing-input or setup failure, a missing or corrupt result artifact, and a completed numeric verdict with an error-shaped field through the real result parser. First classify the failure unit: missing whole-run input or a failed run-level configuration check rejects the run; a selected sample with missing or corrupt required evidence becomes a failure row (below); a completed numeric verdict survives a later cleanup failure. A failure that skips this classification and becomes a plain score is a violation, and a strict failure policy written by this PR does not authorize it (its provenance is checked under L5); the same zero on another backend is not coverage, it is the same violation on a second path; a model's own missing deliverable that the grader scores numerically is a scored outcome, not an infrastructure failure, but a numeric value is not proof of a verdict: when the upstream grading wrapper catches an exception and writes a numeric sentinel (`overall_score: 0` with an error), that branch is a judge failure, so a remedy keyed on "a number is present" must still separate it. A test that expects the implementation's zero is not evidence that zero is allowed. Before proposing a scoring fix, check its after-state on three cases separately: a model outcome with a numeric verdict (keep the score), a completed verdict followed by a cleanup or teardown failure (keep the verdict), and missing or corrupt required input or result evidence for a sample (a failure row with its `error_kind`, outside `success_samples`, counted by the metric's failure rule in `score_including_errors` as item 10 describes; never a completed verdict graded from the broken evidence with a flag such as `complete: false`, and never a silent zero without a failure row). Missing input for the whole run raises instead (P9, 15f). A fix that is right for one case and wrong for another is the wrong fix.
10. **Input modes (items 8, 9).** Check each input mode against its own obligation. `local_data_dir` is a canonical data-source arg (item 12) and the repository's offline override, so reading a user-supplied directory through it is not an item 8 violation by itself. A mode the benchmark uses by default or for a supported backend that reads data without `dloaders` (a prepared template, a bundled directory) can violate item 8 without proving that item 9's hosting rule is violated: establish where its data comes from before asserting a hosting problem. Read mutual-exclusion guards before proposing a comparison with a dataset pin; when a mode has no selected pin, name the missing provenance contract instead of a pin that does not apply. The proposed fix names the source identity that mode can carry and the shared loader that would enforce it; comparing against a pin the constructor forbids is not a fix.

Map a finding onto the guideline instead of arguing it from first principles. Cite the item in the report and the checklist; in the comment, name `GUIDELINE.md` and state the rule in words without its number (house rule G2).

## CI semantics (Phase 5)

- `wbl-eval-param-lint` runs `make param-check`. Green proves spec shape (exhaustiveness, no generation params in `args:`, name collisions, base signatures, grouping and order, timeout suffixes). It proves nothing about whether a value reaches the model; that is L2.
- Success is the literal line `param-standardize: 위반 없음 ✅`, not merely exit 0.
- The lint skips vendored trees and dot-directories by design, so a finding inside `{bench}/src/**` is never lint-caught. That is L6.
- A new vendored tree must be excluded in four places: `[tool.ruff]` and `[tool.mypy]` excludes in `eval/wbl-eval/pyproject.toml`, the monorepo root `pyproject.toml` ruff exclude, and root `pants.toml` `pants_ignore`. The root ones are commonly missed because a bench-local `make lint` still passes.
- CI runs only for PRs whose base matches `on.pull_request.branches` in `.github/workflows/ci.yaml` (read it at `target_sha`); a stacked PR into any other branch gets no CI at all. GitHub runs it on the merge with the base, not on the head alone.
- Some contract tests are outside the CI test jobs (the guideline marks `tests/test_summary_contract.py` as not run by CI). Check the workflows' test selection, and run the contract tests the change touches in the merge candidate (Phase 5.4).

## Running code safely here

- Run tests and probes in `WT` with its own environment, never in the user's checkout. Some benchmark imports download data or models on import (the param lint imports every benchmark), which would otherwise land in a shared `.venv`.
- Live tests: pass `-k "not smoke"`, and deselect `*_integration.py` tests that start real evaluations (some start paid sandbox or model runs when credentials exist). Run suites in a credential-less tree.
- No paid model, sandbox, or cluster runs without the user's explicit approval.
